# Phase 04.3: CLAP-First Product Rebaseline — Context

**Gathered:** 2026-08-20
**Status:** Ready for planning
**Source:** User-approved product rebaseline after Phase 04.2 live verification

## Phase Boundary

Reconcile the product and remaining roadmap around the verified hybrid CLAP architecture. This phase does not replace the bridge, daemon, Pi runtime, or CLI, and it does not rewrite completed phase history. It closes the gap between the original external-Pi product assumptions and the in-Bitwig workflow now proven in Phase 04.2.

## Locked Decisions

### Product surface

- The hosted CLAP editor is the primary producer-facing interface.
- Confirmed project/track/instance/clip scope, Analyze, proposal inspection, approval, Arm, Stop, and session fork remain in the CLAP workspace.
- Long content must be readable: the proposal/conversation region needs wrapping plus vertical scrolling and must not depend on widening the Bitwig editor beyond the display.
- Device-panel parameters remain compact status and ordinary musical controls; action buttons stay hosted UI commands.

### Responsibility boundaries

- The Java controller extension is the authoritative Bitwig reader and mutator.
- The TypeScript daemon owns normalized state, policy, focus, project/instance sessions, proposal lifecycle, approval dispatch, and persistence.
- Pi 0.84 remains a daemon-managed, project-scoped reasoning runtime with bounded tools. It proposes but cannot directly apply, arm, access sockets/filesystem, or receive raw audio.
- The CLAP audio callback remains real-time safe and limited to transparent forwarding, bounded aggregates, and exact approved MIDI scheduling.
- The CLI remains supported for automation, diagnostics, test drivers, recovery, and alternate agents, but it is not the primary human UX.

### Arrangement workflow

- Phase 4 analyzers and CLI commands remain valid implementation assets.
- The old external Pi `/review` and arrangement-pane acceptance wording is superseded by a CLAP-native arrangement review flow.
- Phase 04.3 must inventory the untracked legacy `04-UAT.md` without deleting or falsely completing it, classify each row as retained CLI coverage, superseded UI coverage, or a real product gap, and create a focused CLAP UAT.
- Arrangement observations and suggestions remain non-destructive unless they yield an inspectable exact-scope proposal through the existing approval authority path.

### Phase 5 contract

- Device and automation workflows are surfaced in the CLAP workspace, not a required external Pi `/device` pane.
- They reuse confirmed scope, proposal revisions, one-shot approval, candidate/pre-flight checks, controller mutation authority, and daemon journal/revert behavior already verified in Phase 04.2.
- Native Bitwig and third-party plug-in chains remain in scope; unsupported host metadata must be shown honestly rather than inferred from names.

### Local-first and providers

- DAW integration, raw project state, authorization, persistence, and mutation remain local.
- Raw audio never leaves the plug-in or enters Pi sessions.
- Non-AI inspection and control continue to work without a remote provider.
- Reasoning may use a local model or an explicitly configured remote provider. Only bounded confirmed context is sent, and only after explicit Analyze.
- Provider absence/auth failure must remain a bounded visible product state, never a silent fallback or a daemon crash.

## Historical Treatment

- Phases 1–4, 03.1, 04.1, and 04.2 remain historical records of what was built and verified.
- Completed Pi skills and CLI commands are not removed merely because their UX role changed.
- Active and future requirements may be superseded with dated wording; completed requirement claims are not reassigned retroactively.

## Planning Targets

1. Documentation and operator-runbook reconciliation.
2. Arrangement analyzer-to-CLAP proposal/read-model integration.
3. Readable scrollable arrangement/proposal presentation.
4. Legacy Phase 4 UAT classification and replacement CLAP UAT.
5. Phase 5 implementation contract and dependency map.

## Deferred

- Editing Bitwig arranger structure directly when the Controller API cannot do so safely.
- A mobile/web client.
- Raw-audio upload or model-side audio processing.
- Broad redesign of the verified Phase 04.2 real-time scheduler or authority boundaries.
