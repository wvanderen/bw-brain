# Phase 04.1: Hybrid CLAP Integration Foundation - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 04.1 adds a thin bw-brain CLAP companion that makes the agent feel native inside Bitwig while preserving the existing safety architecture. The plug-in provides a focused hosted UI, per-track real-time MIDI/audio feature extraction, and sample-accurate playback of explicitly approved MIDI. The external daemon remains authoritative for project/session state, Pi remains outside the plug-in process, the CLI remains the stable automation contract, and the Java controller extension remains the only component allowed to mutate existing Bitwig project state.

This phase establishes the companion plug-in, multi-peer/instance identity contract, daemon-owned Pi session integration, real-time-safe telemetry/output boundary, and in-Bitwig approval UX. It does not replace the controller extension or daemon, inspect arbitrary Bitwig project state through CLAP, send raw audio outside the plug-in, make proactive suggestions, perform background edits, or create an autonomous continuous-generative mode.

</domain>

<decisions>
## Implementation Decisions

### First Useful Plug-in Experience

- **D-01 — Focused workspace:** The full plug-in window is a musical decision workspace, not a clone of Pi's terminal. Conversation is primary, with current Bitwig context, connection state, and proposal review immediately available.
- **D-02 — Three-pane flow:** Use a compact context strip, central conversation, and a proposal drawer that appears only when there is something to inspect or approve.
- **D-03 — Essential device controls:** When the full window is closed, Bitwig's device panel still exposes connection/session status, Analyze, Stop, a proposal-pending indicator, and a small set of automatable musical controls.
- **D-04 — Quiet startup:** A new instance connects silently, identifies its track/instance, and shows a concise ready state with suggested actions. It does not automatically analyze, prompt Pi, or generate suggestions.

### Real-time Boundary

- **D-05 — Continuous telemetry, on-demand reasoning:** Lightweight feature extraction may run continuously while the instance processes signal, but no telemetry is sent to Pi and no suggestion is produced until the user asks.
- **D-06 — Aggregates only:** Note events and bounded aggregate features may leave the plug-in process. Candidate audio features include density, velocity, pitch-class profile, loudness, transient activity, spectral bands, and stereo width. Raw audio never leaves the plug-in process and is not retained by the daemon.
- **D-07 — Approved live MIDI only:** Pi may prepare a bounded phrase/variation off the audio thread. The user must inspect and arm the exact material before the plug-in schedules it sample-accurately. Continuous autonomous generation is out of scope.
- **D-08 — Transparent fail-safe:** If the daemon or Pi disconnects, original audio/MIDI continues untouched. Generated material stops at a safe musical boundary, required note-offs are sent, and the UI/device indicator becomes visibly disconnected.

### Instance and Session Model

- **D-09 — One project session, many instance contexts:** The daemon owns one Pi session per Bitwig project. Each CLAP instance contributes track-scoped context to that session rather than creating an independent agent.
- **D-10 — Confirmed identity link:** Each plug-in has a persistent instance ID and reports available CLAP track metadata. The controller and daemon correlate the selected track/device, followed by a one-time user confirmation. Track-name heuristics alone are never authoritative.
- **D-11 — Focused-instance targeting:** The instance being interacted with becomes the active prompt target. The context strip always names the target track/instance; requests spanning multiple instances require explicit scope selection.
- **D-12 — Project-local persistence and safe forks:** Reopening a project resumes its Pi session. Duplicated plug-ins receive new instance IDs but join the same project session. Save As forks the session so the new project can diverge without contaminating the source project's history.

### Approval Flow Inside Bitwig

- **D-13 — UI approves, controller mutates:** For existing clips/project state, the CLAP UI displays the daemon's validated patch and diff and collects approval. Only the controller extension performs the mutation through the existing candidate-store, pre-flight, patch-history, and inverse-operation path.
- **D-14 — Arm then boundary-launch:** Approved live MIDI is inspected first, armed explicitly, and launched on the next configured beat/bar boundary with a visible countdown.
- **D-15 — One-shot scope-bound approval:** Approval covers one exact proposal revision and target instance/clip. Any content revision or target change invalidates approval and requires a new preview.
- **D-16 — Stop generated behavior, preserve the song:** Global Stop cancels queued/generated MIDI at a safe boundary, sends necessary note-offs, and disarms all instances. It does not alter original signal or silently revert already-applied journaled edits; project revert remains a separate explicit action.

### the agent's Discretion

- Choose the native CLAP implementation language/framework after research, provided it supports all target platforms and strict real-time separation.
- Choose the concrete GUI toolkit and visual styling within the locked three-pane/product behavior.
- Define exact bounded feature schemas, sampling cadence, queue structures, and default beat/bar launch quantization.
- Choose whether CLAP peers use a dedicated loopback endpoint or a peer-aware evolution of the current transport, while preserving loopback-only access, version negotiation, and authoritative routing.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `Transport`, `LineBuffer`, correlator, and schema-validated reader: reusable framing and request/response machinery for CLAP peers, but routing must become peer-aware.
- `CandidateStore`, `PatchHistory`, `previewPatch`, and inverse operations: retain unchanged as the sole existing-project edit trust spine behind CLAP approvals.
- `StaleWatchdog` and structured `stateFreshness`: reusable for per-peer connection and degraded-mode UI, likely generalized to controller/Pi/instance health.
- Analyzer registry and arrangement/role stores: reusable project context that can enrich on-demand prompts without moving reasoning into the plug-in.
- Pi skills and CLI tools: retain as a parallel UX and stable fallback while the new hosted UI talks to the same daemon authority.

### Established Patterns

- Validate every cross-process boundary against a versioned schema; never trust raw peer messages.
- Keep callbacks non-blocking and isolate I/O from host/audio threads. The CLAP process callback must perform bounded lock-free work only.
- Bind network services to loopback only; never widen the existing local-first boundary.
- User intent must be acknowledged or failed explicitly; no silent loss of apply/arm/stop actions.
- Existing project mutations require a previewed patch, exact scope, risk handling, journal entry, and recoverable inverse.

### Integration Points

- Extend the daemon from one implicit controller peer to explicit peer identities and capabilities: controller, CLAP instance, Pi runtime, and CLI client.
- Preserve controller TCP/JSON-Lines authority or isolate it behind a dedicated endpoint; do not let CLAP socket fan-out receive controller-targeted edits.
- Add a daemon-side project-session manager around Pi SDK or RPC, with project identity, Save As fork semantics, event streaming, and restricted bw-brain tools.
- Add a native `clap/` module for pass-through processing, lock-free feature/event queues, aggregate telemetry, approved phrase buffers, state/parameter extensions, and the focused GUI.
- Add controller-assisted one-time instance-to-track linking without weakening the current wrong-target pre-flight.

</code_context>

<specifics>
## Specific Ideas

- The intended visual shape is a compact context strip, central conversation, and an on-demand proposal drawer—not a terminal embedded in a plug-in frame.
- “Real time” means signal-local observation and sample-accurate execution, not continuous agent reasoning or unsolicited suggestions.
- The plug-in should feel immediately ready after opening while remaining quiet until asked.
- The full UI and compact device controls share the same visible states: ready, analyzing, proposal pending, armed/counting down, playing generated material, stopping, and disconnected.
- Target identity must always be legible; convenience must never reintroduce the wrong-clip/wrong-track failure Phase 03.1 closed.

</specifics>

<deferred>
## Deferred Ideas

- Autonomous continuous-generative mode or persistent trust windows.
- Proactive background Pi analysis/suggestions.
- Raw audio capture, audio snippet retention, audio mastering, or stem processing.
- Replacing the controller extension with CLAP or using CLAP to mutate existing Bitwig clips directly.
- Cross-project global Pi memory; project copies fork rather than share active session history.

</deferred>
