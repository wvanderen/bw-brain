## User Constraints (from CONTEXT.md)

### Locked Decisions

### First Useful Plug-in Experience

- **D-01 — Focused workspace:** The full plug-in window is a musical decision workspace, not a clone of Pi's terminal. Conversation is primary, with current Bitwig context, connection state, and proposal review immediately available.
- **D-02 — Three-pane flow:** Use a compact context strip, central conversation, and a proposal drawer that appears only when there is something to inspect or approve.
- **D-03 — Essential device controls:** When the full window is closed, Bitwig's device panel still exposes connection/session status, Analyze, Stop, a proposal-pending indicator, and a small set of automatable musical controls.
- **D-04 — Quiet startup:** A new instance connects silently, identifies its track/instance, and shows a concise ready state with suggested actions. It does not automatically analyze, prompt Pi, or generate suggestions.

### Real-time Boundary

- **D-05 — Continuous telemetry, on-demand reasoning:** Lightweight feature extraction may run continuously while the instance processes signal, but no telemetry is sent to Pi and no suggestion is produced until the user asks.
- **D-06 — Aggregates only:** Note events and bounded aggregate features may leave the plug-in process. Candidate audio features include density, velocity, pitch-class profile, loudness, transient activity, spectral bands, and stereo width. Raw audio never leaves the plug-in process and is not retained by the daemon.
- **D-07 — Approved live MIDI only:** Pi may prepare a bounded phrase/variation off the audio thread. The user must inspect and arm the exact material before the plug-in schedules it sample-accurately. Continuous autonomous generation is out of scope.
- **D-08 — Transparent fail-safe:** If the daemon or Pi disconnects, original audio/MIDI continues untouched. Generated material stops at a safe musical boundary, required note-offs are sent, and the UI/device indicator becomes visibly disconnected.

### Instance and Session Model

- **D-09 — One project session, many instance contexts:** The daemon owns one Pi session per Bitwig project. Each CLAP instance contributes track-scoped context to that session rather than creating an independent agent.
- **D-10 — Confirmed identity link:** Each plug-in has a persistent instance ID and reports available CLAP track metadata. The controller and daemon correlate the selected track/device, followed by a one-time user confirmation. Track-name heuristics alone are never authoritative.
- **D-11 — Focused-instance targeting:** The instance being interacted with becomes the active prompt target. The context strip always names the target track/instance; requests spanning multiple instances require explicit scope selection.
- **D-12 — Project-local persistence and safe forks:** Reopening a project resumes its Pi session. Duplicated plug-ins receive new instance IDs but join the same project session. Save As forks the session so the new project can diverge without contaminating the source project's history.

### Approval Flow Inside Bitwig

- **D-13 — UI approves, controller mutates:** For existing clips/project state, the CLAP UI displays the daemon's validated patch and diff and collects approval. Only the controller extension performs the mutation through the existing candidate-store, pre-flight, patch-history, and inverse-operation path.
- **D-14 — Arm then boundary-launch:** Approved live MIDI is inspected first, armed explicitly, and launched on the next configured beat/bar boundary with a visible countdown.
- **D-15 — One-shot scope-bound approval:** Approval covers one exact proposal revision and target instance/clip. Any content revision or target change invalidates approval and requires a new preview.
- **D-16 — Stop generated behavior, preserve the song:** Global Stop cancels queued/generated MIDI at a safe boundary, sends necessary note-offs, and disarms all instances. It does not alter original signal or silently revert already-applied journaled edits; project revert remains a separate explicit action.

### the agent's Discretion

- Choose the native CLAP implementation language/framework after research, provided it supports all target platforms and strict real-time separation.
- Choose the concrete GUI toolkit and visual styling within the locked three-pane/product behavior.
- Define exact bounded feature schemas, sampling cadence, queue structures, and default beat/bar launch quantization.
- Choose whether CLAP peers use a dedicated loopback endpoint or a peer-aware evolution of the current transport, while preserving loopback-only access, version negotiation, and authoritative routing.

### Deferred Ideas (OUT OF SCOPE)

- Autonomous continuous-generative mode or persistent trust windows.
- Proactive background Pi analysis/suggestions.
- Raw audio capture, audio snippet retention, audio mastering, or stem processing.
- Replacing the controller extension with CLAP or using CLAP to mutate existing Bitwig clips directly.
- Cross-project global Pi memory; project copies fork rather than share active session history.

## Summary

Build this as a new `clap/` C++17/CMake target using JUCE for cross-platform audio/MIDI and the native editor, plus the free-audio `clap-juce-extensions` adapter pinned as a reviewed git dependency. The adapter is explicitly unofficial and incomplete, so Wave 0 must prove four capabilities in Bitwig before product work: stereo audio/MIDI pass-through, sample-offset MIDI output, hosted editor lifecycle, and access (or graceful absence) of CLAP track metadata. [CITED: https://github.com/free-audio/clap-juce-extensions] The official CLAP ABI remains the contract, and `clap-validator` plus live Bitwig 6.x checks are mandatory. [CITED: https://github.com/free-audio/clap] [CITED: https://cleveraudio.org/developers-getting-started/]

Do not attach CLAP instances to the current controller `TcpServerTransport`: its `send()` deliberately broadcasts to every socket, its reader has no connection identity, and its correlator assumes one implicit bridge peer. [VERIFIED: codebase `daemon/src/transport/tcp.ts`, `daemon/src/protocol/reader.ts`, `daemon/src/protocol/correlator.ts`] Add a dedicated loopback CLAP endpoint with per-connection framing, handshake, outbound queue, peer ID, capabilities, and targeted sends; leave controller TCP and CLI UDS behavior stable. The daemon becomes the sole project-session/router authority, while the plug-in audio callback only performs pass-through, bounded feature accumulation, bounded lock-free queue operations, transport/boundary math, and ordered MIDI event insertion.

Identity and approval require explicit state machines. A persisted plug-in `instanceId` survives reopen, but duplication copies state; the daemon must detect a simultaneously connected duplicate ID, mint a replacement, and have the duplicate persist it. CLAP state alone cannot identify a Bitwig project or reliably detect Save As; project-session identity therefore needs controller/daemon metadata plus an explicit fork workflow when the project identity changes. [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/ext/state.h] Existing-project edits must reuse `CandidateStore`, wrong-clip pre-flight, bridge `apply.patch`, `PatchHistory`, and inverse operations unchanged. [VERIFIED: codebase `daemon/src/query/query-server.ts`, `daemon/src/patch/`, `bridge/src/main/java/com/bwbrain/bridge/PullHandlers.java`]

**Primary recommendation:** Establish the host/RT/identity protocol in testable vertical slices before building the conversation UI: CLAP shell → peer-aware daemon → confirmed link/project session → telemetry → proposal/approval → armed sample-accurate MIDI → Pi streaming UI.

### Pattern 1: Three-domain plug-in separation

**What:** Treat audio, worker/network, and UI/main threads as separate actors. Communication is immutable snapshots over fixed-capacity SPSC queues or atomics; only worker/UI code allocates, parses JSON, performs I/O, locks, or invokes Pi.

**When to use:** Every signal, telemetry, connection, status, proposal, and control path.

```cpp
// Source: CLAP lifecycle/process contract
ProcessResult process(AudioBlock& block, MidiBuffer& midi) noexcept {
  passThroughAudioInPlace(block);
  featureAccumulator.consume(block, midi);       // bounded, preallocated
  telemetryQueue.tryPush(featureAccumulator.snapshotIfDue());
  phraseScheduler.mergeApprovedEvents(midi);     // sample-sorted, bounded
  return ProcessResult::Continue;
}
```

Official CLAP marks `process()` as audio-thread work, bounds frames at activation, and requires output events in sample order. [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/plugin.h] [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/process.h]

### Pattern 2: Per-connection peer registry, never broadcast

**What:** A dedicated loopback server owns `PeerConnection` objects keyed by a daemon-issued `connectionId`, then binds an authenticated `peerKind`, `instanceId`, `projectId`, negotiated version, capabilities, and health. `sendTo(peerId, message)` is the only outbound primitive.

**When to use:** All CLAP traffic and later any multi-peer daemon traffic.

The current `TcpServerTransport.send()` fans every message to every socket; reusing it would leak phrases, approval state, and controller requests across instances. [VERIFIED: codebase `daemon/src/transport/tcp.ts`]

### Pattern 3: Collision-aware instance identity

**What:** Persist `instanceId` in CLAP state. On connect, the daemon checks the live `(projectId, instanceId)` lease. No collision means reopen/reconnect; a simultaneous collision means duplication, so the later peer receives `instance.rekey`, persists the new ID, and calls the host state-dirty mechanism. Link state is separate: `unconfirmed → confirmed(trackSid/device link) → stale/unlinked`.

**When to use:** Load, duplicate, reconnect, track move/rename, and project Save As.

CLAP state is used for reload and duplication, so copied state cannot alone tell those cases apart. [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/ext/state.h]

### Pattern 4: Revision-bound proposal capability

**What:** Daemon hashes/canonicalizes proposal content and issues a one-use approval record containing `proposalId`, `revision`, `projectId`, `instanceId`, optional `clipSid`, operation kind, and expiry. Approval, arm, and apply revalidate every field and atomically consume the token. Content or target change creates a new revision and invalidates the old token.

**When to use:** Both journaled patches and live MIDI phrases. For patches, token consumption calls the existing edit handler rather than a new mutation path.

### Pattern 5: Owned-note ledger and bounded stop

**What:** Track every generated note-on by stable phrase/note identity. On Stop/disconnect/deactivation/reset, cancel future generated events and emit matching note-offs at the selected safe boundary, with an immediate bounded fallback before process suspension. Never suppress or synthesize note-offs for original input notes.

**When to use:** Launch, global Stop, peer loss, transport stop/jump, plug-in reset/deactivate, phrase replacement.

### Anti-Patterns to Avoid

- **Socket/JSON/logging in `processBlock()`:** any syscall, allocation, mutex, JSON parse, file write, or UI callback can violate real-time constraints.
- **One shared TCP broadcaster:** it cannot preserve peer confidentiality, routing, or request correlation.
- **Track name as identity:** names are mutable and non-unique; only confirmed controller correlation is authoritative.
- **Persisting daemon session state inside a plug-in instance:** duplicates and Save As would alias/fork incorrectly and sandbox crashes could lose authority.
- **A second apply implementation for the CLAP UI:** it would bypass pre-flight, risk, inverse, and journal invariants.
- **Treating “Analyze” as continuous Pi traffic:** continuous local aggregation is allowed; transmission/reasoning begins only after explicit user action.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| CLAP ABI/lifecycle | Custom ABI wrapper | Official CLAP headers + reviewed adapter | Thread annotations, extension negotiation, event ordering, bundle ABI. |
| Cross-platform editor embedding | Cocoa/Win32/X11 parents from scratch | JUCE editor through CLAP adapter | Host parenting, scale, resizing, input and teardown are platform-specific. |
| Project mutation/revert | CLAP-to-Bitwig edit path | Existing candidate/pre-flight/controller/journal path | Already encodes the safety contract. |
| Pi conversation engine | Custom chat/session persistence | Official Pi SDK in daemon | SDK owns messages, streaming, compaction, session navigation/fork. [CITED: https://pi.dev/docs/latest/sdk] |
| Cross-process message trust | Ad hoc JSON/type casts | Versioned JSON Schemas + compiled validators | Existing project standard prevents protocol drift. |
| Lock-free primitive | Novel concurrent queue | Small audited bounded SPSC implementation from JUCE/adapter or a reviewed dependency | Memory ordering and lifetime bugs become audio corruption/crashes. [ASSUMED] |

**Key insight:** the new work is coordination, not a new authority stack. Reuse the CLAP ABI, native GUI framework, Pi runtime, and existing patch journal; hand-written code should be limited to bw-brain-specific state machines, schemas, features, and routing.

## Common Pitfalls

### Pitfall 1: “Persistent ID” duplicates persistently

**What goes wrong:** Copying a plug-in copies its state and therefore its `instanceId`; two live devices claim one identity.

**How to avoid:** live lease collision + daemon-issued rekey for the later connection; persist after rekey; test reopen versus duplicate separately.

### Pitfall 2: Save As silently shares Pi history

**What goes wrong:** The current daemon derives durable paths from `process.cwd()` and bridge project summaries do not carry robust project identity. [VERIFIED: codebase `daemon/src/runtime/boot.ts`, `bridge/.../PullHandlers.java`]

**How to avoid:** introduce a project registry (`projectId`, lineage/source ID, display metadata, session file) and explicit confirmed fork. If Bitwig cannot expose a definitive save path/event, surface “Fork session for this project copy” rather than infer from a name.

### Pitfall 3: Controller messages reach plug-ins

**What goes wrong:** current TCP `send()` broadcasts; a controller `apply.patch` or pull request can arrive at every CLAP socket.

**How to avoid:** dedicated port/server and targeted per-peer send. Add a negative integration test proving CLAP peers never receive controller envelopes.

### Pitfall 4: UI action bypasses one-shot scope checks

**What goes wrong:** UI renders revision A but approves revised content B, or focus changes to another track before apply.

**How to avoid:** daemon-owned proposal revision and target capability; consume once; rerun existing live `clipSid` pre-flight immediately before controller apply.

### Pitfall 5: Pass-through fails on layout/precision/aliasing

**What goes wrong:** unexpected mono/stereo layout, double precision, in-place alias, bypass, or zero-event blocks mute/change original signal.

**How to avoid:** explicitly support mono/stereo 32-bit and 64-bit or reject unsupported layouts at activation; property-test bit-transparent pass-through; no latency/tail unless introduced intentionally.

### Pitfall 6: Hanging generated notes

**What goes wrong:** disconnect/reset/deactivate occurs after note-on and before scheduled note-off.

**How to avoid:** generated-note ownership ledger, lifecycle flush, transport discontinuity handling, and test every teardown point. CLAP reset explicitly kills voices/processing state; plug-in output obligations must be resolved before suspension where possible. [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/plugin.h]

### Pitfall 7: Unsafe telemetry implementation

**What goes wrong:** FFT allocation, locks, or full-resolution feature history grows on the audio thread; worker lags and queue grows without bound.

**How to avoid:** fixed-size windows and accumulators, precomputed coefficients, fixed cadence (recommend 10 Hz UI snapshots and at most 2 Hz daemon aggregate summaries while an explicit analysis request is active), drop/coalesce oldest telemetry only, never raw samples. Cadences are [ASSUMED] defaults to tune in UAT.

### Pitfall 8: Framework wrapper hides required CLAP behavior

**What goes wrong:** sample offsets, track-info, state-context, or device-panel controls are missing or translated incorrectly.

**How to avoid:** Wave 0 capability plug-in and adapter seam; direct CLAP-extension shim only where needed; do not start full UI until Bitwig evidence is recorded. The adapter itself documents incomplete translation and explicit sample-event-resolution configuration. [CITED: https://github.com/free-audio/clap-juce-extensions]

### Pitfall 9: Sandboxing assumptions break cross-instance state

**What goes wrong:** static/global memory is assumed shared, but Bitwig hosting mode can isolate plug-ins in different processes.

**How to avoid:** every instance independently connects to the daemon; no cross-instance globals or shared-memory requirement. [CITED: https://www.bitwig.com/learnings/plug-in-hosting-crash-protection-in-bitwig-studio-20/] [CITED: https://www.bitwig.com/userguide/latest/vst_plug-in_handling_and_options/]

### Required Invariants

- **RT-1:** audio callback performs zero heap allocation, blocking lock, filesystem/network I/O, JSON, or logging; instrument allocation count and worst-case callback duration.
- **RT-2:** original audio and input MIDI are unchanged for disconnected, idle, analyzing, proposal-pending, armed-before-boundary, and stopping states.
- **RT-3:** telemetry memory and work are bounded for max advertised block size/channel count; overflow coalesces/drops telemetry only.
- **MIDI-1:** every generated note-on has exactly one note-off across normal completion, Stop, disconnect, reset, deactivate, transport stop/jump, and phrase replacement.
- **ROUTE-1:** controller traffic reaches only controller; phrase/UI traffic reaches only target instance; no peer can claim another peer's capability.
- **AUTH-1:** unconfirmed instances cannot prompt, approve, arm, or mutate; consumed/stale revision tokens always fail closed.
- **JOURNAL-1:** every existing-state mutation still produces the same patch history and inverse semantics as CLI apply/revert.
- **SESSION-1:** reopen resumes; duplicate rekeys; Save As forks; source and fork histories diverge.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---|---|---|
| V2 Authentication | yes | Daemon-issued peer connection identity plus confirmed instance-track link; loopback alone is not identity. |
| V3 Session Management | yes | Project-scoped Pi session, live instance leases, expiry/revocation on disconnect, fork lineage. |
| V4 Access Control | yes | Capability matrix: controller may mutate; CLAP may request/approve/arm only for its confirmed scope; CLI remains separate. |
| V5 Input Validation | yes | JSON Schema/Ajv at daemon boundaries; bounded C++ decode; size/count/range limits before queueing. |
| V6 Cryptography | limited | Use platform/Node CSPRNG UUIDs and SHA-256/canonical digest; do not invent crypto. Loopback transport is not encrypted. |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Local process impersonates CLAP/controller peer | Spoofing | Separate endpoints, peer-kind handshake, confirmation link, short-lived daemon capabilities; controller mutation endpoint never accepts CLAP message types. |
| Peer changes proposal/target after preview | Tampering | Canonical content digest + revision + exact project/instance/clip scope; atomic one-shot consume. |
| Approval/apply cannot be reconstructed | Repudiation | Existing patch journal plus proposal/approval audit record without raw audio. |
| Cross-instance proposal/conversation leak | Information disclosure | targeted sends; per-project/instance authorization; negative routing tests. |
| Telemetry/message flood | Denial of service | max frame/message sizes, bounded queues, cadence limits, coalesce observational telemetry, never block audio. |
| CLAP peer invokes controller mutation | Elevation of privilege | capability allowlist and reuse of daemon edit handler; no direct bridge handle exposed to peer router. |

Loopback binding must remain explicit (`127.0.0.1`/validated loopback); never omit the host argument. [VERIFIED: existing `TcpServerTransport` guard]

## Phase 04.2 Suggested Product Decomposition (Planning Input Only)

The following is non-executable input for `$gsd-plan-phase 04.2` after this gate completes. Phase 04.1 implements none of these product slices.

1. **Wave 0 — native/host spike and contracts:** pin stack, add CMake/CI/test harness, prove CLAP/Bitwig capabilities, freeze peer and state schemas.
2. **Peer routing foundation:** dedicated per-connection server, handshake/capabilities, targeted correlation, health, reconnect, size/backpressure limits; leave controller TCP untouched.
3. **Identity/session foundation:** project registry, instance lease/rekey, controller-assisted confirmation, focus target, reopen/Save As fork tests.
4. **RT plane:** transparent processor, fixed feature accumulators/SPSC snapshots, network worker, schemas; prove no raw audio and no unsolicited Pi.
5. **Live MIDI plane:** immutable bounded phrase, revision approval, quantized scheduler, generated-note ledger, global Stop/disconnect lifecycle.
6. **Existing-edit UI adapter:** proposal/diff stream and approval command that delegates to existing preview/apply path; journal equivalence tests.
7. **Pi session service:** SDK adapter with restricted bw-brain tools, one runtime/project, event streaming, cancel/dispose/fork, fake-backed tests.
8. **Hosted UX:** shared UI state model, context strip/conversation/proposal drawer, compact params/indicators, accessibility and live Bitwig UAT.

The decomposition intentionally proves routing, identity, and RT safety before the visually expensive UI. Each later slice consumes a stable contract rather than inventing authority inside the editor.
