## Implementation Decisions

### Clip-ID Source Strategy (the foundation — apply pre-flight + revert reliability both depend on it)

- **D-01 — clipSid binding invariant (source = researcher's call):** `state.selection.clipSid` is **stable across note edits on the same clip** (so revert can target it), matches `^clip_[0-9a-f]{16}$`, and is populated by the bridge on every `get.selected_clip` response AND every `clip.name_changed` event. The **launcher-clip NAME accessor** is the preferred source (the P2 PENDING slot — `getLoopLength()` is the proxy today); a content-only fingerprint is **brittle** (changes on edit, breaks revert targeting — explicitly rejected as the sole source). The researcher's live in-app probe determines whether the name accessor is available, whether unnamed clips need a fallback (and what that fallback is), and the exact hash construction. Binding invariants the researcher cannot violate: stable-across-edits, matches the STATE-04 pattern, populated on both push and pull paths.
- **D-02 — clipSid is durable (persists across daemon restart):** The clipSid-to-clip mapping persists in `.bw-brain/state-cache.json` (P2 MEM-01 durable memory) so a daemon restart can re-target revert operations on patches minted before the restart. On reconnect, the daemon reconciles the persisted clipSid against live bridge reality via the existing `refreshSnapshot` path (no new reconciliation code). This is required because `patch-history.jsonl` is durable and revert must work post-restart.
- **D-03 — clipSid propagates on BOTH push event + pull response:** The `clip.name_changed` event payload **carries the clipSid** (daemon updates `selection.clipSid` immediately — the event already fires live per P2 UAT, only the payload is empty today) AND the `get.selected_clip` response carries it (pull). Apply pre-flight reads `selection.clipSid` from the daemon's live state directly — no extra round-trip at apply time. The frozen JSON-Lines protocol extends minimally (the `clip.name_changed` event payload gains one field; no new message type).

### Apply Pre-Flight Strictness (the trust-spine gate the M4 UAT proved missing)

- **D-04 — Apply REFUSES on clipSid mismatch:** At `bw-edit apply`, the daemon refuses with a structured error when the cursor clip's live `clipSid` ≠ the preview-time `clipSid` captured in the candidate store (D-05 P3). The producer must re-select the preview clip (or re-preview). This is the minimum invariant that prevents the observed M4 UAT failure (320 ops silently landing on an 8-bar clip instead of the 4-bar previewed clip). P3 D-04 two-step explicit flow is unchanged — this adds the **third trust-spine invariant** at apply time.
- **D-05 — Revert gets the SYMMETRIC gate:** `bw-edit revert <patchId>` refuses with the same structured error when the cursor clipSid ≠ the clipSid recorded in `patch-history.jsonl` for that patchId. Revert-to-wrong-clip is the same trust-spine failure as apply-to-wrong-clip — the gate is symmetric. `patch-history.jsonl` entries gain a `clipSid` field stamped at apply time (additive — old entries with no clipSid are pre-fix and stay caveated).
- **D-06 — Refusal shape = structured hard error + recovery hint:** `{ok:false, error:"wrong_clip_targeted", expectedClipSid, actualClipSid, hint:"re-select the clip you previewed (or re-preview)"}`. Matches the existing D-04 structured-failure family (`confirmation_required` / `candidate_not_found` / `below_bar_requires_confirm`). No `y/N` interactive prompt — consistent with D-04 two-step explicit. The Pi `/apply` + `/diff` skills match on `error:"wrong_clip_targeted"` and surface the hint.

### Bridge Auto-Reconnect (the asymmetric gap — daemon already reconnects cleanly, bridge does not)

- **D-07 — Exception-driven reconnect (no heartbeat):** Socket write/read failure (Java `SocketException` / `IOException` on the Outbox writer thread or the pull thread) → null out the socket field → re-enter the retry loop. Synchronous detection, no polling lag, **zero protocol change** (preserves the frozen JSON-Lines contract — no new ping message type). Heartbeat is explicitly rejected: it would require extending the frozen protocol, adding daemon-side scheduling, and tuning a heartbeat-timeout — the cost is disproportionate when the bridge writes constantly while connected (loss is detected on the next failed write). Loopback-only (P1 Pitfall 5) preserved throughout.
- **D-08 — `startConnector` becomes a lifecycle loop:** `BridgeExtension.startConnector` is refactored from "retry-until-first-connect then exit" to `while(running){ connect → run writer+pull until socket loss → null socket → retry }`. The 1s retry interval + loopback-only constraint are preserved. The Outbox writer thread + PullHandlers pull thread cleanly stop on socket loss (interrupt + drain) and restart on the next successful connect. One path serves both first-connect and reconnect — no separate `startReconnect()` method.
- **D-09 — Daemon-side reconcile is AUTOMATIC via existing `refreshSnapshot`:** No new daemon-side reconciliation code path. The daemon's existing `bridgePoll` (`boot.ts:251`, every 2.5s) already detects `false→true` socket transitions and runs `refreshSnapshot()` (which pulls `get.project_summary` + `get.selected_clip`). When the bridge reconnects, the daemon auto-reconciles: clipSid is re-derived from the reconnected bridge + cross-checked against `.bw-brain/state-cache.json` (D-02). No producer action required.

### Skill-Prompt Stale Semantics (align Pi prompts with the relaxed daemon gate)

- **D-10 — Literal realignment across `/vary` `/apply` `/diff`:** The three Pi skill prompts state explicitly that `live` AND `stale` are both **trustworthy** (the daemon pulls fresh state per `bw-midi vary` / `bw-edit apply` / `bw-edit revert` call — the gate refusal on `stale` was already removed in commit `7a7e7cf`); only `disconnected` (no bridge) is a hard refusal. Strip the stale-as-untrustworthy language from all three SKILL.md files. No skill contradicts the daemon gate. The daemon gate (commit `7a7e7cf`: refuse only on `disconnected`) is the contract the skills match.
- **D-11 — All three skills updated symmetrically:** `/vary`, `/apply`, `/diff` shell out to the same daemon that applies the same relaxed gate — treating them inconsistently would be incoherent. The contract tests (`pi-pack/skills/*/skill.test.ts`) are updated to assert the new prompt language (no stale-as-untrustworthy phrasing) per the P3 Plan 03-05 BLOCKER-02 vitest-include discipline.

### Scope Boundary

- **D-12 — Stay scoped to the four named bugs:** M1 (native undo step-count) + M5 (techno profile comparison) Phase-3 live UATs are explicitly **out of scope** for 03.1. They stay on Phase 3's books (or get their own micro-phase). 03.1 is a tight trust-spine gap-closure, not a UAT-completion phase. M1 refines only the user-facing undo caveat (it does NOT change the daemon-authoritative spine per P3 D-03); M5 exercises existing vary code with `profile:techno` — both are exploration, not bug-fix.

### the agent's Discretion
- **Exact clipSid hash construction (D-01):** the binding invariant is "stable-across-edits + matches `^clip_[0-9a-f]{16}$`"; whether the hash is `sha256(name + trackSid).slice(0,16)` or some other construction is the researcher's call after the live name-accessor probe.
- **Unnamed-clip fallback (D-01):** if the launcher-clip name accessor returns empty string for unnamed clips, the researcher picks the fallback (e.g. derive from `loopBeats` + scene index + trackSid). The invariant is "every clip has a non-empty clipSid."
- **`clip.name_changed` event payload schema extension (D-03):** the researcher pins the exact field name + JSON shape (e.g. `{type:"clip.name_changed", payload:{clipSid, name}}`). The invariant is "the daemon learns the clipSid from the event without a pull."
- **Outbox behavior on socket loss (D-07/D-08):** drop queued events or replay-on-reconnect — the invariant is "no producer-visible inconsistency; the daemon's `refreshSnapshot` is the source of truth after reconnect." Researcher picks.
- **`patch-history.jsonl` migration (D-05):** old entries without `clipSid` are pre-fix; the researcher decides whether revert of a pre-fix entry is caveated or refused. Invariant: "post-fix entries always carry clipSid."

## Specific Ideas

- The user's recurring stance — *"below-threshold = refuse rather than guess"* (P3 D-08) — extends to clip identity: **refuse rather than silently target the wrong clip.** D-04 is the apply-time expression of the same stance. The structured `wrong_clip_targeted` error is the trust-spine equivalent of the `status:"refused"` candidate.
- *"Accurate first; creative later"* (PROJECT Core Value) is why 03.1 ships before any new creative capability — the trust spine must be airtight before P4 arrangement / P5 automation lean on it.
- The asymmetric-reconnect observation (D-09): the **daemon already reconnects cleanly**; only the **bridge side** is the gap. The fix is bridge-only (`BridgeExtension.java`); the daemon's `refreshSnapshot` path is reused as-is. This is the smallest honest fix.
- The "literal realignment" choice for D-10 (vs richer live/stale indicators) reflects the user's preference for minimal, honest prompts — the daemon gate is the contract; the skills echo it without dramatization.
- The "stay scoped to 4 bugs" choice (D-12) reflects the user's tight-boundary discipline — 03.1 is a gap-closure, not a kitchen-sink phase; M1/M5 belong elsewhere.
