## Clip-ID source strategy

### Q1 — What should clipSid be sourced from?

| Option | Description | Selected |
|--------|-------------|----------|
| Launcher-clip NAME accessor | Probe in-app whether PinnableCursorClip exposes a stable name (P2 PENDING slot); hash name+trackSid into STATE-04 pattern. Human-meaningful, survives note edits. Cons: requires live probe; empty for unnamed clips. | |
| Content fingerprint | Hash the clip's note-set into STATE-04 pattern. No probe needed. Cons: CHANGES on edit → revert targeting breaks. | |
| Both: name-first, content-fallback | Name accessor first; content fingerprint for unnamed clips. Cons: dual code path; fallback still has the changes-on-edit problem. | |
| You decide | Invariant: stable across edits + matches pattern + populated on push and pull. | ✓ |

**User's choice:** You decide
**Notes:** Locked invariant — clipSid is stable across note edits on the same clip (so revert can target it), matches `^clip_[0-9a-f]{16}$`, populated on every `get.selected_clip` + `clip.name_changed`. Launcher-clip name accessor preferred; content-only rejected as brittle (breaks revert). Researcher's live probe determines name-accessor availability + unnamed-clip fallback.

## Apply pre-flight strictness

### Q1 — What is the apply-time pre-flight check?

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse on clipSid mismatch | REFUSE if cursor clipSid ≠ preview-time clipSid. Minimum that prevents observed M4 UAT failure (320 ops on wrong clip). | ✓ |
| Refuse on clipSid mismatch OR content drift | Refuse if clipSid ≠ OR note-set changed beyond threshold (catches external edits). Cons: drift-threshold tuning; false positives. | |
| You decide | Invariant: apply cannot silently land on a clip other than the previewed one. | |

**User's choice:** Refuse on clipSid mismatch
**Notes:** The candidate store (D-05) records preview-time clipSid; apply compares it to live cursor clipSid. Producer re-selects or re-previews. P3 D-04 two-step explicit unchanged; this adds the third trust-spine invariant.

### Q2 — Does bw-edit revert ALSO get the clipSid pre-flight gate?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — revert gets same gate | Revert refuses if cursor clipSid ≠ clipSid recorded in patch-history.jsonl. Symmetric trust-spine. | ✓ |
| No — revert stays permissive | Revert is recovery; producer's responsibility to aim cursor. Cons: same wrong-clip corruption as apply. | |
| You decide | Invariant: revert cannot silently mutate a clip other than the original patch's clip. | |

**User's choice:** Yes — revert gets same gate
**Notes:** patch-history entries gain a clipSid field at apply time. Old pre-fix entries stay caveated. Symmetric — revert-to-wrong-clip is the same failure as apply-to-wrong-clip.

### Q3 — What shape does the wrong-clip refusal take?

| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** Structured hard error + recovery hint
**Notes:** Pi `/apply` + `/diff` skills match on `error:"wrong_clip_targeted"` and surface the hint.

## Bridge auto-reconnect

### Q1 — How should the bridge detect socket loss + reconnect?

| Option | Description | Selected |
|--------|-------------|----------|
| Exception-driven reconnect | SocketException on write/read → null socket → re-enter retry loop. Synchronous detection, zero protocol change. Cons: detects only when traffic flows. | ✓ |
| Heartbeat-driven reconnect | Daemon pings bridge every Ns; M misses → reconnect. Detects idle loss. Cons: new ping msg type in frozen protocol + scheduler + tuning. | |
| Both (exception + heartbeat) | Belt and suspenders. Cons: max code surface; protocol work still needed. | |
| You decide | Invariant: bridge re-establishes socket without producer intervention; loopback-only preserved. | |

**User's choice:** Exception-driven reconnect
**Notes:** No protocol change — preserves frozen JSON-Lines contract. Heartbeat rejected (disproportionate cost; bridge writes constantly while connected).

### Q2 — Where does the reconnect logic live?

| Option | Description | Selected |
|--------|-------------|----------|
| Reuse startConnector as lifecycle loop | while(running){connect; run writer+pull until loss; null socket; retry}. 1s retry + loopback preserved. | ✓ |
| Separate reconnect method | Cleaner separation first-connect vs reconnect. Cons: duplicates retry-loop logic. | |
| You decide | Invariant: one retry loop serves both; loopback + 1s retry preserved. | |

**User's choice:** Reuse startConnector as lifecycle loop
**Notes:** Writer + pull threads cleanly stop on socket loss; restart on next successful connect.

### Q3 — What happens on the DAEMON side after the bridge reconnects?

| Option | Description | Selected |
|--------|-------------|----------|
| Automatic (reuse refreshSnapshot) | Daemon's existing bridgePoll (boot.ts:251, 2.5s) detects false→true + runs refreshSnapshot. Auto-reconciles clipSid + selection. | ✓ |
| Manual re-sync | Producer triggers re-sync after reconnect. Defeats auto-reconnect's purpose. | |
| You decide | Invariant: daemon reconciles via existing refreshSnapshot path; no new reconciliation code. | |

**User's choice:** Automatic (reuse refreshSnapshot)
**Notes:** Daemon-side reconnect was ALREADY clean (P2 boot.ts:234-262). The gap is bridge-side only. Zero new daemon reconciliation code path.
