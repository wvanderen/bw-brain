## Accomplishments
- D-08 shipped: the bridge reconnects automatically after a daemon restart. `startConnector` is now a `while (running)` lifecycle loop that re-enters CONNECT after each socket loss — one path serves first-connect + reconnect.
- Pitfall 2 defeated: `Outbox.reset()` re-arms the `startWriterThread` CAS (which was a NO-OP after the first `stop()`) and nulls the stale writer-thread reference, so the writer restarts cleanly on each reconnect.

- Defensive `exit()` close: live-connection shutdown now closes the published socket so the pull thread's `readLine` unblocks and the loop exits cleanly.
- Two JUnit 5 proofs: `OutboxResetTest` (Pitfall 2 regression) + `BridgeExtensionReconnectTest` (D-08 reconnect against real loopback ServerSockets). Full bridge suite green: 26/26.

## Decisions Made
- **Lifecycle-loop extraction (plan option (a)):** `BridgeExtension` extends `ControllerExtension` whose ctor requires a live Bitwig `ControllerHost`, so the class cannot be instantiated in a plain JUnit run. The D-08 lifecycle loop was therefore extracted into the package-private static `runConnectorCycle(...)` taking functional-interface params (`BooleanSupplier isRunning`, `Consumer<Socket> setSocket`, `Consumer<String> logger`). Production `startConnector` wraps it in a literal `while (running)`; the test drives it directly with a loopback `ServerSocket` harness and null cursorClip/observers (safe because no inbound request lines arrive in the reconnect scenario — `PullHandlers.runLoop` just blocks on `readLine` and exits on socket close).
- **Pull thread as the loss detector:** the writer thread is NOT a reliable socket-loss detector (it blocks on `queue.take()` during idle periods and won't notice a half-open loss). The pull thread's `readLine` throws/returns-null on socket close, so `pull.join()` returning is the reliable signal. This matches RESEARCH §D-08 detail #4.
- **stop() + reset() + clear() ordering:** the cycle calls `outbox.stop()` (idempotent interrupt of the possibly-parked writer), then on the next iteration `outbox.reset()` (re-arm CAS + null writerThread) before `startWriterThread`. `outbox.clear()` runs in the NULL+RETRY phase to drop queued events.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] OutboxResetTest harness double-accept deadlock**
- **Found during:** Task 1 GREEN (first test run hung)
- **Issue:** The RED draft called `server.accept()` on BOTH the reader thread and the main thread — only one accept succeeds; the other blocks forever, hanging the test.
- **Fix:** Removed the redundant main-thread `server.accept()` calls; the reader thread owns the accept exclusively (mirrors the OutboxTest.java pattern).
- **Files modified:** bridge/src/test/java/com/bwbrain/bridge/OutboxResetTest.java
- **Verification:** OutboxResetTest 3/3 green in ~1s (was hanging).
- **Committed in:** d80796b (Task 1 GREEN — harness fix folded in)

**2. [Rule 1 - Bug] BridgeExtensionReconnectTest observation race (fast reconnect)**
- **Found during:** Task 2 GREEN (two iterations: offered-into-dying-queue, then null-window-miss)
- **Issue:** (a) `waitFor(liveSocket != null)` returned against the OLD socketA reference still published before cycle 1 nulled it — the test then offered "after-reconnect" into the dying cycle-1 queue, which `clear()` wiped. (b) After fixing to wait for `liveSocket == null` first, the null-window between cycles was sub-millisecond on loopback (cycle 2 reconnects instantly), so the 10ms poll never observed the null state.
- **Fix:** Capture the first socket reference and wait for `liveSocket` to publish a DIFFERENT, non-null socket (`cur != null && cur != firstSocket`). This is robust against the fast-reconnect race.
- **Files modified:** bridge/src/test/java/com/bwbrain/bridge/BridgeExtensionReconnectTest.java
- **Verification:** BridgeExtensionReconnectTest 3/3 green in ~0.13s (was failing/timing out).
- **Committed in:** 04a0556 (Task 2 GREEN — race fix folded in)
