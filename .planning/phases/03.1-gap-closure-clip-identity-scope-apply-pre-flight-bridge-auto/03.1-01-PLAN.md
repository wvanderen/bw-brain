<objective>
Close the asymmetric bridge reconnect gap surfaced by the 2026-07-04 M4 UAT (docs/bitwig-capabilities.md §2 line 162): the daemon already reconnects cleanly via `bridgePoll` (boot.ts:251), but the bridge dies silently on socket loss — `Outbox.writerLoop` and `PullHandlers.runLoop` exit on IOException without notifying `BridgeExtension`, and `startConnector` exits after the first successful connect. The producer must toggle the Bitwig controller off/on to recover.

This plan refactors `BridgeExtension.startConnector` (line 82-105) from "retry-until-first-connect then exit" to a `while(running)` lifecycle loop (D-08), and adds `Outbox.reset()` + `Outbox.clear()` (D-07) so the writer thread re-arms on each reconnect (Pitfall 2 — the AtomicBoolean CAS at Outbox.java:70 cannot re-arm without reset). Zero protocol change; loopback-only (Pitfall 5) preserved throughout.

Purpose: Make the bridge self-healing so a daemon restart (common during development + the live UAT) does not require producer intervention. This is the asymmetric gap — the daemon side (D-09) already works via `bridgePoll` + `refreshSnapshot`.
Output: Refactored `Outbox.java` + `BridgeExtension.java` + 2 new JUnit 5 tests proving the reconnect mechanics.
</objective>
