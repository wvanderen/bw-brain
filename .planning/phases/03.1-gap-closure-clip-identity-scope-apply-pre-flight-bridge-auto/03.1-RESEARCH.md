### §D-01 Resolution — clipSid source + hash construction + unnamed-clip fallback

**[VERIFIED: javap extension-api:21.jar + codebase grep] The launcher-clip NAME accessor is NOT available.**

The `Clip` interface (which `PinnableCursorClip` extends via `CursorClip`) was inspected via `javap -classpath ~/.m2/repository/com/bitwig/extension-api/21/extension-api-21.jar com.bitwig.extension.controller.api.Clip`. The full surface includes:

- `public abstract void setName(java.lang.String);` — a name SETTER exists
- **NO `getName()`, `name()`, `title()`, or any String-returning name reader**
- `getTrack()` → `Track` (the parent track, which DOES have `.name()`)
- `getLoopLength()`, `getLoopStart()`, `getPlayStart()`, `getPlayStop()` → `SettableBeatTimeValue` (beat positions)
- `clipLauncherSlot()` → `ClipLauncherSlot` (which has `isSelected()`, `hasContent()`, `color()` but NO slot-index or name accessor — verified via `javap ClipLauncherSlot`)
- `color()` → `SettableColorValue`
- Inherited from `ObjectProxy`: `exists()`, `createEqualsValue(ObjectProxy)` (object-identity equality, requires a second proxy reference — not useful for the cursor-clip pattern)

**Corroborating evidence (all `HIGH` confidence):**
- `bridge/.../Observers.java:104-116` comment: *"the public Clip/CursorClip surface has no name() accessor (Clip extends ObjectProxy; the launcher-clip NAME accessor is pending Task-3 live verification)"* — the PENDING slot D-01 referenced.
- `daemon/src/ingest/fold-event.ts:105-111` `clip.name_changed` case is a documented **NO-OP** for this exact reason.
- `docs/bitwig-capabilities.md §6` (Stable IDs): *"NO stable-id accessor exists on Track — full method scan of com.bitwig.extension.controller.api.Track shows only position() + name() as identity-like accessors; no id()/uuid()/guid()/hash() on Track (or on the Clip/Device surfaces surveyed)."*
- Codebase grep for `clipSid|clip\.name|getName` in `bridge/`: **zero** hits for any clip-name read call (only `cursorTrack.name()`, `cursorDevice.name()`, `trackBank.getItemAt(i).name()`).

**Note on `setName(String)`:** the bridge CAN write a clip name but cannot read it back. Authoring a deterministic name via `setName("bw-brain-<hash>")` is **rejected** — it mutates the producer's clip name (hostile UX) and still doesn't let the bridge distinguish a bw-brain-authored name from a producer-set one on restart.

#### D-01 (a) — The V1 clipSid construction (RECOMMENDED)

Given the verified API constraints, the only identity signals available for a launcher cursor clip WITHOUT adding new observer groups are:

| Signal | Accessor | Stable across note edits? | Stable across clip resize? | Discriminating? |
|--------|----------|---------------------------|----------------------------|-----------------|
| trackSid | `cursorClip.getTrack().name()` → STATE-04 fingerprint | ✅ | ✅ | narrows to track, not clip |
| loop length (beats) | `cursorClip.getLoopLength().get()` | ✅ | ❌ (changes on resize) | narrows within track |
| clip color | `cursorClip.color()` / `clipLauncherSlot().color()` | ✅ | ✅ | producer-settable, weak |

The V1 construction satisfying the D-01 binding invariants:

```typescript
// sha256 over the cursor clip's stable-via-note-edit identity tuple.
// Format: "clip_" + 16 hex chars → matches ^clip_[0-9a-f]{16}$ + STATE-04 family.
clipSid = "clip_" + sha256(`${trackSid}:${loopBeats}`).slice(0, 16);
```

**Invariant check:**
- ✅ **Stable across note edits** — `trackSid` (STATE-04 fingerprint of the parent track) and `loopBeats` (`getLoopLength().get()`) do NOT change when notes are added/removed/edited. This is the exact failure mode the M4 UAT observed (320 ops landed on an 8-bar clip instead of the 4-bar previewed clip — different `loopBeats` → different clipSid → pre-flight catches it).
- ✅ **Matches `^clip_[0-9a-f]{16}$`** — `sha256(...).slice(0,16)` is 16 lowercase hex chars.
- ✅ **Matches STATE-04 family `^(trk|clip|dev)_[0-9a-f]{16}$`** — the `clip_` prefix aligns with the existing pattern in `schemas/project-state.schema.json:63`.

**Computed in the BRIDGE** (it holds the `PinnableCursorClip` proxy; the daemon cannot reach `getLoopLength()`), propagated via the D-03 push + pull paths.

#### D-01 (b) — Unnamed-clip fallback (RESOLVED)

There is no "named vs unnamed" distinction because the name is unreadable. **Every clip gets the V1 hash construction** — the invariant "every clip has a non-empty clipSid" is satisfied unconditionally (the hash inputs `trackSid` + `loopBeats` are always present when a cursor clip exists; `ObjectProxy.exists()` guards the empty case).

#### D-01 (c) — RESIDUAL RISK (must surface to planner + discuss-phase)

**The V1 clipSid collides for two clips on the SAME track with the SAME loop length.** Within one track the cursor can only sit on one clip at a time, so the collision is not a runtime ambiguity *within a single selection* — but the pre-flight D-04 gate compares `previewClipSid` vs `liveClipSid`, and if the producer previews clip A then selects clip B (same track, same length) and applies, the clipSids MATCH and the pre-flight does NOT catch the wrong-clip targeting.

**Mitigations considered:**
1. **Add `color()` to the hash** — `sha256(trackSid:loopBeats:colorRgb)`. Disambiguates clips of different colors on the same track. Still collides for same-color same-length clips. Cheap, low-risk, **recommended as part of V1** if `color()` reads reliably (it is a `SettableColorValue` — `.get()` may block; needs probe).
2. **Add a `ClipLauncherSlotBank` observer** to track the selected clip's scene index. Fully robust (scene index disambiguates within track) BUT it is a new observer group + windowed-bank lifecycle — more surface area than a "tight gap-closure phase" should take on. **Defer to a roadmap item.**

**Recommendation to planner:** ship V1 with `trackSid:loopBeats` (optionally `+color`). This closes the **observed** M4 UAT failure (4-bar vs 8-bar — different loopBeats). Document the same-length-same-track collision as a known limitation; add a `checkpoint:human-verify` task for the clipSid construction so a human confirms the hash inputs read reliably on live Bitwig before the gate goes live.

**Confidence:** `HIGH` that the name accessor is unavailable (javap-verified); `MEDIUM` on the V1 hash robustness (closes observed failure, residual same-length risk documented).

### §D-03 Resolution — event payload + response schema extension

**[VERIFIED: schemas/protocol/event.schema.json:23-35, envelope.schema.json, request.schema.json] The extension is a single additive payload field on each of two existing message types. NO new message type.**

#### D-03 (a) — `clip.name_changed` event payload (push path)

`event.schema.json` payload currently has `additionalProperties: false` with properties `{trackId, clipId, deviceId, slot, name, playing}`. To carry clipSid, **add one property**:

```jsonc
// schemas/protocol/event.schema.json → properties.payload.properties (additive)
"clipSid": {
  "type": "string",
  "pattern": "^(trk|clip|dev)_[0-9a-f]{16}$",
  "description": "STATE-04 fingerprint of the clip (D-03 push). Populated by the bridge on every clip.name_changed event. The daemon folds this into selection.clipSid immediately."
}
```

The emitted line shape becomes:
```json
{"version":"1.0","type":"clip.name_changed","timestamp":1782512568,"payload":{"clipSid":"clip_a1b2c3d4e5f60718"}}
```

The `envelope.schema.json` payload is *"open object at the envelope level; constrained per message-type sub-schema"* — no envelope change. The `reader.ts` Ajv gate validates against the event sub-schema; adding `clipSid` to the allowed payload keeps the trust-spine intact.

#### D-03 (b) — `get.selected_clip` response payload (pull path)

The `response.schema.json` payload is open (responses echo arbitrary `{id, ok, payload}` — `LineJson.response` in `LineJson.java:44-52`). The bridge's `PullHandlers.buildClipResponse` (PullHandlers.java:68-80) builds the payload Map; **add `clipSid` to the top level of that Map**:

```jsonc
// PullHandlers.buildClipResponse — additive top-level field alongside "notes"
{
  "notes": [ {key, pitch, start, length, velocity}, ... ],
  "clipSid": "clip_a1b2c3d4e5f60718"
}
```

The response schema does NOT need a frozen `clipSid` field (response payloads are open by design — `LineJson.response(id, ok, Map<String,?>)` carries arbitrary maps). The **daemon side** reads `resp.clipSid` in (1) `handleMidiInspect` query-server.ts:466 + (2) a new fold into `state.selection.clipSid` from the refreshSnapshot path.

#### D-03 (c) — Daemon-side fold (the push handler)

`daemon/src/ingest/fold-event.ts:105-111` currently NO-OPs `clip.name_changed`. Replace the NO-OP with a `selection.clipSid` fold:

```typescript
case "clip.name_changed": {
  const clipSid = typeof p.clipSid === "string" ? p.clipSid : undefined;
  if (clipSid === undefined) return state; // defensive — bridge always sends it post-D-03
  return { ...state, selection: { ...state.selection, clipSid } };
}
```

#### D-03 (d) — Daemon-side pull reconcile (the gap CONTEXT.md glossed)

**[VERIFIED: boot.ts:177-207] `refreshSnapshot` currently pulls ONLY `get.project_summary` — NOT `get.selected_clip`.** CONTEXT.md says *"refreshSnapshot pulls get.project_summary + get.selected_clip"* — this is slightly inaccurate against the live code. The `refreshSnapshot` body (boot.ts:177-207) issues exactly ONE correlator request: `correlator.send("get.project_summary")`.

**Implication for D-03 pull path:** on a cold reconnect, `selection.clipSid` is re-populated by the FIRST `clip.name_changed` event (push path, D-03 a/c) — which fires when the cursor clip's `getLoopLength()` changes (i.e. when the producer next selects a clip). If the producer does NOT change selection after a reconnect, `selection.clipSid` stays at its persisted value (D-02) until the next clip-change event. That is acceptable for the trust-spine (the persisted clipSid is the one the daemon boot reconciled against).

**Optional hardening (planner's call):** extend `refreshSnapshot` to ALSO `correlator.send("get.selected_clip")` and fold the returned `clipSid` into `state.selection.clipSid`. This makes the reconnect reconcile immediate rather than lazy. Low-risk, additive. **Recommend including** so the apply pre-flight has a fresh clipSid on reconnect without waiting for a producer selection.

**Confidence:** `HIGH` on the schema extension mechanics; `HIGH` on the fold; `MEDIUM` on whether to extend refreshSnapshot (recommend yes).

### §D-07/D-08 Resolution — bridge reconnect lifecycle + outbox behavior on socket loss

**[VERIFIED: BridgeExtension.java:82-105, Outbox.java:78-94, PullHandlers.java:127-139] The exception-driven reconnect + lifecycle loop approach is sound; one detail in CONTEXT.md needs correction.**

#### Current state (the gap)

#### D-08 — The lifecycle loop refactor (validated)

Refactor `BridgeExtension.startConnector` (line 82-105) from "retry-until-first-connect then exit" to:

```java
// BridgeExtension.java — refactored startConnector (D-08)
private void startConnector(final PinnableCursorClip cursorClip) {
    connectorThread = new Thread(() -> {
        while (running) {
            Socket s = null;
            try {
                // (1) CONNECT — retry until connected or running goes false.
                while (running && s == null) {
                    try {
                        s = new Socket(LOOPBACK, PORT); // loopback-only (Pitfall 5)
                        host.println("[bw-brain] connected to daemon " + LOOPBACK + ":" + PORT);
                    } catch (final Exception e) {
                        try { Thread.sleep(1000); } // daemon not up yet; retry
                        catch (final InterruptedException ie) {
                            Thread.currentThread().interrupt(); return;
                        }
                    }
                }
                if (s == null) return; // running went false during connect retry
                socket = s; // publish for exit()'s cleanup
                // (2) RUN — start writer + pull threads, JOIN until both exit.
                //     On socket loss, the writer/pull threads' try-with-resources
                //     closes the socket + the thread exits; join() returns.
                outbox.startWriterThread(s);
                final Thread pull = PullHandlers.start(s, outbox, cursorClip, observers);
                try { pull.join(); } catch (final InterruptedException ie) {
                    Thread.currentThread().interrupt(); return;
                }
                // (3) NULL + RETRY — null the published socket so exit() does not
                //     double-close; loop back to (1).
                socket = null;
                outbox.stop(); // idempotent — resets running for next startWriterThread
            } catch (final Exception e) {
                host.println("[bw-brain] connector loop error: " + e.getMessage());
            }
        }
    }, "bw-brain-connector");
    connectorThread.setDaemon(true);
    connectorThread.start();
}
```

**Critical details the planner MUST get right:**
1. **`outbox.running` is an `AtomicBoolean` (Outbox.java:37) set false by `stop()` and never reset.** `startWriterThread` (Outbox.java:69-76) guards with `running.compareAndSet(false, true)` — so after the first connect, subsequent `startWriterThread` calls are NO-OPS unless `stop()` is called first. **The reconnect loop MUST call `outbox.stop()` before re-entering the run phase, AND `Outbox` must expose a `reset()` (or `startWriterThread` must be re-callable after `stop()`).** This is a non-trivial Outbox change — flag it as a plan task.
2. **`outbox.stop()` interrupts the writer thread (Outbox.java:97-102).** After the writer drains/exits on socket loss, calling `stop()` post-hoc is safe (idempotent interrupt).
3. **`PullHandlers.start` creates a fresh thread each call (PullHandlers.java:118-125).** No reset issue on the pull side.
4. **Loopback-only invariant (BridgeExtension.java:32 `LOOPBACK = "127.0.0.1"`)** is preserved — the reconnect opens `new Socket(LOOPBACK, PORT)` identically to the first connect.
5. **`exit()` (BridgeExtension.java:107-120)** currently interrupts `connectorThread` + `pullThread` + stops outbox. With the lifecycle loop, `connectorThread.interrupt()` unblocks `pull.join()` (via InterruptedException) and the loop checks `running` (set false by `exit()`). **`exit()` must also close the live `socket` if non-null** — currently it relies on the writer/pull try-with-resources. Add a defensive `if (socket != null) try { socket.close(); } catch (...)` to `exit()`.

**CONTEXT.md accuracy check:** D-08 says *"One path serves both first-connect and reconnect — no separate `startReconnect()` method."* — **CONFIRMED sound.** The single `while(running)` loop handles both. The `join()` on the pull thread is the socket-loss detection mechanism (writer thread death alone is insufficient because the writer may be blocked on `queue.take()` with nothing to write — the PULL thread is the reliable detector because `readLine()` throws on socket close).

**Actually — correction to the above.** The writer thread is NOT a reliable detector either: `queue.take()` blocks independent of the socket. The pull thread IS the reliable detector: `in.readLine()` throws `IOException` on socket close. So `pull.join()` returning is the signal. BUT — if the daemon closes the socket while the bridge is NOT being pulled (no inbound request), `readLine()` still throws because the socket is closed. ✅ sound.

**One nuance:** if the socket is half-open (TCP RST lost), `readLine()` blocks until the OS TCP keepalive timeout (potentially minutes). The D-07 exception-driven approach detects LOSS-ON-WRITE (the writer's next `out.write()` throws) but NOT quiet half-open loss. CONTEXT.md D-07 acknowledges this: *"the bridge writes constantly while connected (loss is detected on the next failed write)"*. **This is an assumption that needs honest validation** — does the bridge actually write constantly? With the 5-observer set firing on GUI changes, yes during active production; but during idle periods (producer steps away), the writer may be blocked on `queue.take()` for minutes. **Flag as a documented limitation; the daemon-side `bridgePoll` 2.5s timeout (boot.ts:251) catches daemon-perceived disconnect independently.** The daemon marks stale/disconnected via the watchdog even if the bridge hasn't noticed yet.

#### §D-07 Discretion — Outbox behavior on socket loss (RESOLVED)

**Decision: DROP QUEUED EVENTS on socket loss; do NOT replay-on-reconnect.** Rationale:
- The daemon's `refreshSnapshot` (D-09) is the source of truth after reconnect — it re-pulls `get.project_summary` (+ optionally `get.selected_clip` per D-03d) and reconciles.
- Replaying stale events risks double-application (the daemon already saw selection.changed before the loss; replaying it post-reconnect re-folds it).
- The Outbox queue is ephemeral by design (Outbox.java:36 — unbounded LinkedBlockingQueue, no persistence).
- **The invariant "no producer-visible inconsistency" holds** because `refreshSnapshot` re-derives the full snapshot; any events lost in flight are superseded by the fresh pull.

**Implementation:** on socket loss, the writer thread exits; the queue is left as-is (the next writer thread drains it). To enforce "drop on loss," either (a) `outbox.clear()` on socket-loss detection, or (b) accept that the queue drains stale events into the NEXT socket — which the daemon's reader will fold as if they were fresh. **(a) is safer.** Add an `Outbox.clear()` method and call it from the connector loop when transitioning run→retry.

**What:** the new `clipSid` field inherits the `^(trk|clip|dev)_[0-9a-f]{16}$` pattern enforcement at THREE boundaries: (1) JSON Schema (event.schema.json payload), (2) Ajv reader gate (reader.ts), (3) daemon fold (fold-event.ts defensively checks `typeof === "string"`). The apply/revert pre-flight (D-04/05) compares clipSids as opaque strings — no re-derivation, no parsing.
**When to use:** always — this is the project's frozen trust-spine discipline (P1 D-01).

### Pattern 2: Exception-driven reconnect (no heartbeat)
**What:** socket loss surfaces as `IOException` on the writer's `out.write()` OR the pull's `in.readLine()`; the dying thread signals via thread-exit (the connector loop `join()`s the pull thread). Zero protocol change.
**When to use:** when the protocol is frozen (JSON-Lines) AND the connection is loopback-only (low loss rate) AND the bridge has frequent I/O (the 5-observer set fires on GUI changes). NOT appropriate for wide-area connections or silent-bridge scenarios.

### Pattern 3: Structured-failure family
**What:** `wrong_clip_targeted` joins `state_disconnected` / `candidate_not_found` / `confirmation_required` / `below_bar_requires_confirm` / `scope_mismatch` / `apply_failed`. Same shape (`{ok:false, error:<code>, ...details}`), same Pi-skill matching pattern (the skill matches on `error:"<code>"`).
**When to use:** every daemon-side refusal. Never a bare `throw` or a `y/N` prompt.

### Anti-Patterns to Avoid
- **Re-deriving clipSid at apply time from current state** — by definition the producer may have selected a different clip; the pre-flight must compare the FROZEN preview-time clipSid (stamped in the candidate) vs the LIVE clipSid. Re-deriving would always match.
- **Heartbeat protocol extension** — explicitly rejected (D-07); would unfreeze the JSON-Lines contract for marginal benefit.
- **Mutating clip name via `setName()` to tag identity** — hostile UX (overwrites producer's clip name) + still not readable back.
- **Extending `refreshSnapshot` to pull `get.selected_clip` AND fold clipSid WITHOUT the D-03c fold-event change** — the two paths must agree; half-implementing creates a state where the push path populates clipSid but the pull path doesn't, or vice versa.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SHA-256 hashing | Custom hash | `java.security.MessageDigest` (bridge) / `node:crypto` (daemon) | JDK/Node built-in; audited; no dep |
| Atomic JSON write | Custom rename | `daemon/src/store/atomic-write.ts` (`atomicWriteJson`) | Already the project primitive; temp-in-dirname + rename |

## Common Pitfalls

### Pitfall 1: The name-accessor assumption (D-01 FOUNDATION)
**What goes wrong:** An implementer reads D-01's "the launcher-clip NAME accessor is the preferred source" and assumes it exists, building the clipSid around `cursorClip.name()`.
**Why it happens:** CONTEXT.md phrases it as "preferred" and defers to research; the deferral was never resolved before planning.
**How to avoid:** **The name accessor DOES NOT EXIST in extension-api:21** (javap-verified §D-01). Use the V1 `sha256(trackSid:loopBeats)` construction. This research resolves the deferral — the planner MUST NOT re-introduce the name-accessor path.
**Warning signs:** any plan step referencing `cursorClip.name()`, `getName()`, or a clip-name reader.

### Pitfall 2: Outbox `running` AtomicBoolean not resettable (D-08)
**What goes wrong:** The refactored connector loop calls `outbox.startWriterThread(newSocket)` on reconnect; the call is a NO-OP because `running.compareAndSet(false, true)` (Outbox.java:70) returns false (running is already true from the first connect).
**Why it happens:** `Outbox.running` is set false only by `stop()` and never reset. The reconnect loop must call `stop()` then re-`startWriterThread()`, but `stop()` also interrupts the writer thread (which is already dead) — idempotent but the `running` flag must transition false→true cleanly.
**How to avoid:** Add an `Outbox.reset()` method (or make `startWriterThread` re-callable after `stop()`). The planner MUST include this as an explicit task — it is the non-obvious dependency of D-08.
**Warning signs:** reconnect succeeds (socket opens) but no events flow to the daemon.

### Pitfall 3: `refreshSnapshot` does NOT pull `get.selected_clip` today (D-03d)
**What goes wrong:** Planner reads CONTEXT.md D-09 *"refreshSnapshot pulls get.project_summary + get.selected_clip"* and assumes both pulls happen. On reconnect, `selection.clipSid` is NOT immediately refreshed (only `get.project_summary` runs).
**Why it happens:** CONTEXT.md is slightly inaccurate against the live code (boot.ts:177-207 issues ONE correlator request).
**How to avoid:** Either (a) extend `refreshSnapshot` to also pull `get.selected_clip` + fold clipSid (recommended), OR (b) accept lazy reconcile (clipSid refreshes on the next `clip.name_changed` event). Document the choice.
**Warning signs:** apply pre-flight uses a stale clipSid immediately after a reconnect.

### Pitfall 4: Same-length-same-track clipSid collision (D-01 RESIDUAL)
**What goes wrong:** Producer previews clip A (4-bar), selects clip B (4-bar, same track), applies — clipSids MATCH (same trackSid + same loopBeats) → pre-flight does NOT catch the wrong-clip targeting.
**Why it happens:** The V1 hash inputs (trackSid, loopBeats) don't disambiguate same-length clips on the same track.
**How to avoid:** (a) Add `color()` to the hash (mitigates, doesn't eliminate), OR (b) defer to a future ClipLauncherSlotBank-based clipSid (fully robust). For 03.1, document the residual risk + ship V1.
**Warning signs:** Two same-length clips on the same track in the producer's project; pre-flight never fires.

### Pitfall 5: Bridge quiet half-open loss (D-07)
**What goes wrong:** Daemon closes the socket but the TCP RST is lost; the bridge's `readLine()` blocks until OS TCP keepalive timeout (minutes); the producer sees no reconnect for a long time.
**Why it happens:** Exception-driven detection catches LOSS-ON-WRITE (next `out.write()` throws) but NOT quiet half-open loss when the bridge has nothing to write.
**How to avoid:** The daemon-side `bridgePoll` (boot.ts:251, 2.5s) independently detects disconnect via `hasConnectedSockets()` — the daemon marks stale/disconnected regardless of bridge awareness. The bridge eventually notices on its next write. **Accept this as a documented limitation**; do NOT add a heartbeat (D-07 rejects it).
**Warning signs:** bridge log shows no reconnect attempt for >30s after a daemon restart, but daemon is up.

### Pitfall 6: NodeNext ESM `.js` import rule (AGENTS.md)
**What goes wrong:** New daemon `.ts` files use `from "./foo"` (no extension) — runtime fails `ERR_MODULE_NOT_FOUND`.
**Why it happens:** NodeNext ESM requires explicit `.js` extensions in import specifiers even when the source is `.ts`.
**How to avoid:** Every new daemon-side `.ts` import ends in `.js` (e.g. `from "../patch/candidate-store.js"`). Existing code is the reference.
**Warning signs:** `npm test` fails with module-not-found on the new files.

### Pitfall 7: Ajv 2020-12 named-import quirk (AGENTS.md)
**What goes wrong:** New schema-validation code imports Ajv as `import Ajv from "ajv"` — fails under NodeNext.
**Why it happens:** ajv 8.20 ships no exports map; the 2020-12 mode is at `ajv/dist/2020.js`.
**How to avoid:** `import { Ajv2020 } from "ajv/dist/2020.js"` (see intent-store.ts:18, query-server.ts:30). `addFormats` is deliberately NOT used.
**Warning signs:** TypeError on Ajv construction.

### Pitfall 8: `safeSendErr` shape extension (D-06)
**What goes wrong:** Implementer adds `wrong_clip_targeted` as a brand-new send function alongside `safeSendErr`, diverging from the structured-failure family.
**Why it happens:** `safeSendErr` currently hardcodes `availableFrom:"M2"`; the new error needs `expectedClipSid`/`actualClipSid`/`hint` instead.
**How to avoid:** Extend `safeSendErr` with an optional `details?: Record<string, unknown>` arg appended to the result object (recommendation in §D-06). Keeps one function, one shape family.
**Warning signs:** two parallel error-send functions in query-server.ts.

## Code Examples

### Example 1 — Bridge clipSid derivation (D-01, new ClipSid.java)
```java
// Source: extension-api:21 javap verification + STATE-04 fingerprint pattern.
// Pure helper; no Bitwig dep so it is unit-testable.
package com.bwbrain.bridge;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public final class ClipSid {
    private ClipSid() {}

    /**
     * D-01 V1 clipSid construction. Stable across note edits (trackSid + loopBeats
     * do not change on note mutation). Matches ^clip_[0-9a-f]{16}$.
     *
     * Residual risk: same-track same-length clips collide. See RESEARCH.md §D-01(c).
     */
    public static String derive(final String trackSid, final double loopBeats) {
        final String input = trackSid + ":" + loopBeats;
        try {
            final byte[] hash = MessageDigest.getInstance("SHA-256")
                    .digest(input.getBytes(StandardCharsets.UTF_8));
            final String hex = HexFormat.of().formatHex(hash).substring(0, 16);
            return "clip_" + hex;
        } catch (final Exception e) {
            // SHA-256 is JDK-guaranteed; unreachable. Fall back to a constant
            // so the daemon's pattern validation still passes (the pre-flight
            // will fire on any mismatch).
            return "clip_0000000000000000";
        }
    }
}
```
