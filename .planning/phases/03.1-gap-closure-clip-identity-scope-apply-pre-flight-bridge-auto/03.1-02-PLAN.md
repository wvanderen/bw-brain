<objective>
Close the M4 UAT critical blocker: `bw-edit apply` can silently land on the wrong clip because `state.selection.clipSid` is never populated. The 2026-07-04 UAT observed 320 ops landing on an 8-bar clip when a 4-bar clip was previewed (docs/bitwig-capabilities.md §2 line 158-160).

This plan populates `state.selection.clipSid` via BOTH paths: the bridge computes a V1 clipSid (`"clip_" + sha256(trackSid:loopBeats).slice(0,16)`, D-01 — the launcher-clip NAME accessor is definitively NOT in extension-api:21 per javap verification), emits it in the `clip.name_changed` event payload (D-03a) AND the `get.selected_clip` response (D-03b); the daemon folds it into `selection.clipSid` on push (D-03c) + pulls it eagerly on reconnect (D-03d, the CONTEXT.md correction — refreshSnapshot currently pulls only `get.project_summary`). Durability is free (D-02) — the existing `schedulePersist` → `.bw-brain/state-cache.json` path already serializes `lastRawState.selection`.

**Task ordering matters:** Task 1 (schema + daemon fold) MUST ship before Task 2 (bridge emits clipSid), because the daemon's Ajv reader gate enforces `additionalProperties: false` on the event payload — a bridge emitting `clipSid` before the schema allows it would have EVERY `clip.name_changed` event rejected.

Purpose: Make clip identity computable + durable so Plan 03's apply/revert pre-flight gates can compare preview-time vs live clipSid.
Output: New `ClipSid.java` pure helper + 4 additive schema/daemon/bridge edits + regenerated TS types.
</objective>
