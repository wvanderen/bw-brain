## Summary

Phase 04.1 has removed the host-level unknowns: Bitwig 6.0.11 loaded a validator-clean CLAP bundle, preserved a non-zero MIDI offset exactly (`32 → 32` after successful output push), hosted a visible resizable Cocoa child view through reopen, exposed fractional musical parameters, supplied track-info with an empty name, and offered no definitive Controller API Save As signal. [VERIFIED: `04.1-VERIFICATION.md`; `docs/bitwig-clap-capabilities.md`] The product must therefore treat CLAP track metadata as a hint, use controller confirmation as identity authority, require explicit `session.fork`, render status/actions in the hosted editor, and expose only genuinely musical controls as host automation parameters. [VERIFIED: `docs/bitwig-clap-capabilities.md` Q1–Q4]

The existing repository contains only the throwaway native probe; there is no production `clap/src`, product build, dedicated CLAP daemon endpoint, session manager, Pi runtime, proposal service, or phrase scheduler. [VERIFIED: codebase inventory 2026-08-10] The current controller TCP transport broadcasts every outbound line to every connected socket and its correlator assumes one implicit bridge, so it cannot safely host CLAP instances. [VERIFIED: `daemon/src/transport/tcp.ts`; `daemon/src/protocol/correlator.ts`] Build a second loopback endpoint with per-peer queues and targeted sends, leaving controller TCP and CLI UDS behavior unchanged.

The safest execution order is narrower than the downstream notes imply: (1) convert the capability-only native build into coexisting capability and product targets; (2) freeze bounded CLAP schemas and targeted peer transport; (3) establish project/instance identity and focus; (4) install and wrap exactly Pi SDK 0.84.0; (5) add aggregate telemetry; (6) add proposals and controller delegation; (7) prove the RT scheduler/note ledger; (8) bind the hosted UI and musical parameters; (9) run cross-platform CI and live Bitwig UAT. Each later stage consumes authority established by the earlier stage; UI-first or Pi-first implementation would create untestable implicit identity and routing.

**Primary recommendation:** Plan nine dependency-ordered slices, with schemas/targeted routing and identity as the first product gate and a pure, independently verified scheduler as the last gate before live arming.

### Pattern 1: Targeted CLAP Peer Endpoint

Use a dedicated configurable loopback port (recommended default `7879`, adjacent to controller `7878`) with maximum line size, handshake timeout, protocol major/minor, peer kind, instance ID, capabilities, and per-connection outbound queue. A `PeerRegistry.sendTo(connectionId, envelope)` primitive must be the only CLAP send path. The existing controller `TcpServerTransport.send()` intentionally fans out and must remain controller-only. [VERIFIED: `daemon/src/transport/tcp.ts`]

Handshake sequence: socket accept → bounded line decoder → `clap.hello` → schema/version/capability check → lease/collision decision → `clap.accept` or `instance.rekey` → optional link confirmation state. No telemetry, prompt, proposal, or phrase is accepted before `accepted && projectBound && instanceConfirmed`.

Security requirements: bind literal loopback only, reject non-loopback configuration, cap line and queue sizes, validate every envelope before dispatch, redact payloads in logs, and close peers that exceed bounds. [VERIFIED: existing loopback/validate-at-boundary conventions in `tcp.ts` and `reader.ts`]

### Pattern 2: Project and Instance Identity State Machines

Persist a random UUID `instanceId` in CLAP state with schema version and musical settings. On connection, the daemon leases `(projectId, instanceId)` to one live connection. A reconnect after the old lease closes resumes; a simultaneous second claimant is a duplicate and receives a new daemon-minted ID which it persists and marks dirty. CLAP state is copied on duplication, so persisted identity alone cannot distinguish duplicate from reopen. [CITED: https://raw.githubusercontent.com/free-audio/clap/main/include/clap/ext/state.h; VERIFIED: Phase 04.1 state-copy evidence]

Keep four identities separate:

| Identity | Authority | Persistence | Rule |
|---|---|---|---|
| `connectionId` | daemon | memory only | New on every socket. |
| `instanceId` | daemon-minted, CLAP-persisted | plug-in state | Rekey only on simultaneous collision. |
| `projectId` | daemon | project-local registry | Never derived from display names or cwd alone. |
| controller correlation | controller-confirmed link | daemon project registry | `trackSid/device hint/instanceId`; names are hints only. |

Link state is `unconfirmed -> confirmationPending -> confirmed -> stale/unlinked`. The UI may show hints while unconfirmed but Analyze, approve, apply and arm fail closed. Focus is a daemon-owned `(projectId, instanceId)` value changed by explicit UI focus and reflected in every editor; proposals retain their original scope even if focus later moves.

For Save As, expose explicit `session.fork(sourceProjectId, newProjectId)` confirmation. Copy durable conversation history into a new Pi branch/lineage, create a new project registry record, rebind instances only after confirmation, and never infer a fork from project, track, device, or window names. [VERIFIED: controller API evidence shows no definitive Save As signal]

### Pattern 3: One Pi Session per Project

Wrap SDK imports behind `PiRuntime` and `PiProjectSession` interfaces. `ProjectSessionManager.getOrOpen(projectId)` owns exactly one session, subscriber set, abort controller, and serialized prompt queue for that project. Instance context is appended as structured scope to each explicit request; it does not create a second Pi session. Tests use a fake runtime and never contact a model or network.

Only the following daemon operations should be exposed to Pi tools: read current confirmed scope/context, create a proposal candidate, and call the same existing read/preview operations available through the CLI trust spine. Do not expose controller sockets, filesystem-wide access, raw audio, direct `apply.patch`, or arm-token minting. The current `pi-pack` documents the `bw-*` CLI as the stable contract, so the adapter should invoke shared handlers rather than invent a second mutation API. [VERIFIED: `pi-pack/README.md`; Phase 04.1 pattern map]

Quiet startup opens/reopens the project session and subscribes to events but never calls `prompt`. `analysis.request` is the sole conversation-triggering operation. `Stop` aborts the active Pi turn and clears queued generated behavior; it does not delete or fork history. Project close unsubscribes and disposes; Save As uses the explicit fork flow.

### Pattern 4: Aggregate-Only Telemetry Plane

The audio callback may update fixed counters/windows for RMS/peak, note density, pitch-class histogram, velocity summary, onset/rhythm bins, transport/tempo/time-signature flags, and bounded recent note events. It may not retain or transmit PCM buffers, FFT frames, arbitrary histories, sysex, or unbounded event lists. This allowlist is a product contract, not merely a UI choice.

Use two cadences: an RT snapshot cadence bounded by a fixed block/sample counter, and a slower daemon publish cadence controlled by the worker. Queue capacity, aggregate array lengths, note count, phrase length, and serialized message bytes must be schema constants. On telemetry queue overflow, drop/replace the oldest aggregate snapshot and increment a visible dropped-snapshot counter; never block the audio thread.

### Pattern 5: Exact Proposal Approval and Controller Delegation

`ProposalStore` owns canonical proposal content and revision. Every proposal contains `proposalId`, `revision`, `kind`, `projectId`, `instanceId`, optional `clipSid`, human-readable rationale, bounded exact material, and assumptions. Any content or target change creates a new revision and invalidates all earlier approvals.

`ApprovalStore.issue` creates an opaque, expiring one-shot capability bound to the canonical content digest plus all scope fields. `consume` must atomically compare and delete before side effects. Reuse, expiry, focus drift, project/instance/clip mismatch, disconnect, revision change, Stop, or fork all fail closed.

For existing-state edits, successful consume delegates to the existing `CandidateStore` → wrong-clip pre-flight → `apply.patch` controller round-trip → inverse/journal path. [VERIFIED: `daemon/src/query/query-server.ts`; `daemon/src/patch/*`; `bridge/.../PullHandlers.java`] Refactor the current private edit handler into a shared service callable by both CLI and proposal dispatch; do not simulate a CLI subprocess and do not duplicate apply logic.

For live MIDI, successful consume produces one immutable `ArmedPhrase` for one instance. It does not touch `PatchHistory`. Global Stop never calls revert and never changes already journaled edits.

### Pattern 6: RT Phrase Scheduler and Owned-Note Ledger

Make `PhraseScheduler` a pure, allocation-free state machine receiving an immutable bounded phrase prepared off-thread. It computes the next configured beat/bar boundary from CLAP transport fixed-point beat position, tempo/time signature flags and block size; launches only when the boundary falls in the current block; and inserts generated events in sample-sorted order with original pass-through events. CLAP output events must be pushed in sample order and `try_push` may fail. [CITED: https://github.com/free-audio/clap/blob/main/include/clap/events.h]

The scheduler must define deterministic fallback states:

- Missing/invalid beat timeline or time signature: remain armed, display `waiting_for_transport`; never guess a wall-clock boundary.
- Transport jump/loop before launch: recompute next eligible boundary.
- Transport stop after launch: cancel future generated events and schedule owned note-offs at offset 0 of the next process block.
- Output push failure: record failure, disarm/cancel remaining generated material, and attempt bounded owned-note cleanup on the next available block.
- Disconnect/Stop/reset/deactivate: cancel future events; emit note-offs for every generated owned note while processing is available; clear ledger after bounded drain. Never create or suppress note-offs for input-owned notes.

Use a ledger key containing generated phrase ID plus note ordinal and the emitted CLAP note address. Note events are addressed by port/channel/key/note_id tuples; wildcard semantics require exact ownership bookkeeping. [CITED: https://github.com/free-audio/clap/blob/main/include/clap/events.h]

### Pattern 7: Hosted UI and Musical Parameters

Use JUCE for the cross-platform product editor (macOS Cocoa, Windows native HWND, Linux X11 where supported by the adapter) and keep platform-specific code behind the adapter/editor host seam. Phase 04.1 directly proved the Cocoa parent/resize/reopen lifecycle only; Windows and Linux require CI bundle/validator coverage and platform UAT before claiming support. [VERIFIED: `docs/bitwig-clap-capabilities.md`]

The UI model has explicit states: connection, identity/link, focused scope, project session, conversation stream, active analysis, proposal revision, approval/arm/countdown, scheduler status, telemetry health, and errors. The proposal drawer is absent—not empty—when no inspectable proposal exists. UI actions enqueue worker commands; the UI never touches sockets or RT objects directly.

Resolved Q3 overrides a literal reading of D-03: Bitwig did not surface the non-automatable Analyze parameter in its device panel, while the embedded editor worked. Therefore place truthful status, Analyze, Stop, and proposal indicator in the hosted editor; expose only ordinary musical controls (for example Generated Mix) as CLAP automatable parameters. [VERIFIED: live Q3 evidence] Parameter changes cross to RT through atomics/parameter facilities, not daemon round trips.

## Common Pitfalls

### Broadcast leakage
**Failure:** A phrase or approval reaches the wrong CLAP instance.  
**Prevention:** Dedicated endpoint, per-peer queues, targeted-send-only API, and a negative three-peer test proving controller and sibling peers receive nothing. [VERIFIED: current TCP broadcasts]

### Identity conflation
**Failure:** Reopen is treated as duplicate, duplicate shares an ID, or Save As shares active history.  
**Prevention:** closed-lease reconnect, simultaneous-collision rekey, explicit project fork, and separate connection/instance/project/link IDs.

### UI approval races focus
**Failure:** revision A displayed on track A applies revision B or track B.  
**Prevention:** approval scope is immutable and revalidated atomically; focus change does not retarget a proposal.

### RT thread contamination
**Failure:** JSON, logging, allocation, mutex, filesystem, DNS/socket, or UI callbacks occur in `process`.  
**Prevention:** static analysis/grep gate plus allocation-counting or instrumentation test around the process path.

### Hanging generated notes
**Failure:** disconnect, transport stop, reset or push failure strands a note-on.  
**Prevention:** generated-only ledger and lifecycle matrix tests at every interruption point.

### “Bounded” only in prose
**Failure:** note arrays, queues, histories, or lines grow from external input.  
**Prevention:** constants in schemas/code, rejection tests at limit+1, queue drop metric, and fuzz/property tests.

### Stop mutates history
**Failure:** global Stop reverts journaled edits or deletes conversation.  
**Prevention:** Stop coordinator owns active Pi abort, pending approvals, armed phrases and generated notes only; journal APIs are not dependencies of Stop.

### Build/license surprise
**Failure:** product uses JUCE without a distribution-compatible license decision or tracks floating git branches.  
**Prevention:** immutable pins already exist; add a release checklist item for JUCE AGPL/commercial disposition. [VERIFIED: dependency lock]
